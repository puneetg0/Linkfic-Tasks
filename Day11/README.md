## Concepts Learned

### PostgreSQL, SQL, and NoSQL

PostgreSQL is a relational database. It stores structured information in tables made up of rows and columns. SQL (Structured Query Language) is the language used to create tables and work with the data in them.

SQL databases such as PostgreSQL are a good fit when data has a consistent structure and records need clear relationships. NoSQL databases, such as MongoDB, can store data in flexible document-style structures. Which type is appropriate depends on the needs of the application.

### Tables, Rows, and Columns

A table stores one kind of related information. A row is one record, and a column is one property of a record. In CineShelf, each row in `movies` represents a movie.

### Primary Keys and Foreign Keys

A primary key uniquely identifies each row. The `movies.id` column is generated by PostgreSQL, so each movie receives its own ID.

A foreign key is a column that points to a key in another table. For example, a future `reviews` table could have a `movie_id` foreign key referring to `movies.id`. That relationship lets the database connect reviews to movies and helps prevent references to movies that do not exist. CineShelf does not have this second table yet.

### Dictionary vs Database

A Python dictionary is useful for data held temporarily while a program runs. A database stores committed data so it can be retrieved after the application restarts and shared by different requests.

### Why Use a Database?

Applications need persistent storage to save information, retrieve it later, update it, and manage it consistently. CineShelf previously used a JSON file; its movie API now uses PostgreSQL.

## SQL Practice

These are the SQL operations I practiced in pgAdmin. In each query, the `WHERE` clause selects which row to change or retrieve.

### Add a movie

```sql
INSERT INTO movies (title, genre, release_year, rating, watched, poster_url)
VALUES ('Inception', 'Sci-Fi', 2010, 8.8, false, NULL);
```

### Read movies

```sql
SELECT id, title, genre, release_year, rating, watched
FROM movies;
```

### Update one movie

```sql
UPDATE movies
SET watched = true
WHERE title = 'Inception';
```

The `WHERE` condition matters: without it, the `UPDATE` would change every row in the table.

## FastAPI and PostgreSQL Connection

SQLAlchemy is the Python toolkit used by the API to communicate with PostgreSQL. Psycopg is the PostgreSQL driver used by SQLAlchemy.

- `backend/.env` stores `DATABASE_URL` locally; `.gitignore` excludes it from Git. Do not put the real password in a presentation, screenshot, or Git commit.
- `backend/database.py` loads the URL, creates the SQLAlchemy engine and session factory, and provides a database session to FastAPI routes.
- `backend/models/db_models.py` describes the PostgreSQL `movies` table as a Python SQLAlchemy model.
- `backend/schemas/movie.py` validates API input and formats movie responses.
- `backend/routes/movie.py` uses database sessions for movie and genre endpoints.
- `backend/migrate_movies.py` imports existing records from `backend/movies.json`.

The connection flow is:

1. FastAPI starts and `backend/database.py` loads `DATABASE_URL` from `backend/.env`.
2. SQLAlchemy creates an engine using that URL. Psycopg provides the PostgreSQL driver.
3. For a request, FastAPI gets a database session from `get_db()`.
4. A route uses the session and `MovieDB` model to run a database query or change a record.
5. PostgreSQL returns the result; FastAPI turns it into a JSON response.

To start the API from the Day 11 project folder:

```powershell
.\backend\.venv\Scripts\python.exe -m uvicorn backend.main:app --reload
```

Keep this terminal open while using the API. The `--reload` option restarts the server when Python files change.

Then open `http://127.0.0.1:8000/docs` to try the endpoints using Swagger UI. Postman can also send requests to `http://127.0.0.1:8000`.

# FastAPI Connected to PostgreSQL

These steps demonstrate both sides of the connection: FastAPI returns database records, and a record created through the API can be seen in PostgreSQL.

1. **Show the database in pgAdmin.** Connect to `cineshelf_dev` as `cineshelf_app` and open Query Tool. Run:

   ```sql
   SELECT current_database(), current_user;
   ```

   This should show `cineshelf_dev` and `cineshelf_app`. Do not show or disclose the password.

2. **Start the backend.** In a terminal at the Day 11 project root, run the Uvicorn command above. Explain that the terminal is running the FastAPI backend.

3. **Show the API documentation.** Open `http://127.0.0.1:8000/docs`. The interactive page is generated by FastAPI.

4. **Read data through the API.** In Postman, send `GET http://127.0.0.1:8000/movies?search=Inception`. The JSON response should include the Inception record that is stored in PostgreSQL.

5. **Create a temporary record.** Send `POST http://127.0.0.1:8000/movies` with **Body → raw → JSON** and this example:

   ```json
   {
     "title": "Presentation Test Movie",
     "genre": "Practice",
     "release_year": 2020,
     "rating": 7.5,
     "watched": false,
     "poster_url": null
   }
   ```

   Note the `id` in the response. It is generated by PostgreSQL.

6. **Prove the API inserted a database row.** In pgAdmin Query Tool, run:

   ```sql
   SELECT id, title, genre, release_year, rating, watched
   FROM movies
   WHERE title = 'Presentation Test Movie';
   ```

   The row returned by this SQL query is the same record Postman created by calling FastAPI.

7. **Show an update.** In Postman, send `PATCH http://127.0.0.1:8000/movies/<id>/watched`, replacing `<id>` with the ID from the create response. Use this JSON body:

   ```json
   {
     "watched": true
   }
   ```

   Run the same `SELECT` query in pgAdmin again and show that `watched` is now `true`.

8. **Clean up the demo record.** Send `DELETE http://127.0.0.1:8000/movies/<id>` using that same ID. Run the `SELECT` query once more; it should return no rows.

Use a temporary example record for the demo. Avoid displaying the `.env` file or any passwords in the presentation.
